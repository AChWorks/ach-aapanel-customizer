# ACh aaPanel Customizer — Development Guidance

Read [the canonical product specification](docs/PROJECT-SPEC.md) before changing product behavior. The Owner-wide operating principle **simplicity and informed choice** applies to every module, old and new.

- Build the smallest maintainable solution that completes a real administrator task; avoid speculative scenarios, duplicate persistence layers, repetitive approval checkboxes, and hardcoded feature restrictions that do not follow from actual system capabilities.
- Do not impose arbitrary version, provider, platform, path, domain, site-count, payload-size or timeout allowlists. Discover the installed environment, paginate native collections, and expose genuinely variable settings rather than encoding a convenient QA value as a product limitation.
- Distinguish necessary protocol, resource and data-integrity bounds from artificial restrictions. Correct authorization, intended target ownership, and prevention of destructive changes to unrelated data are not optional.
- For acceptable residual uncertainty, show a short **nonmandatory** pre-action note explaining impact and useful checks. An authorized administrator's explicit action is consent: perform the supported operation without requiring all suggestions to be completed or adding a second checkbox.
- Keep errors, results, recovery information and the actual supported scope truthful. A warning cannot make an incorrect or loss-causing write safe; do not pretend an unfamiliar writer is supported when its target format is unknown.
- When touching an older flow, reconcile it with the latest Owner decision, simplify documented obsolete gates, add focused regression tests, and keep the nearest relevant README/technical guide and owning Issue consistent. Historical source-bound evidence remains historical, not an absolute future-version ban.
- Native UI form-row contract: reuse the shared `.ach-controls` row with a nested `.ach-inline-field` wrapping its `label` and `select/input`. Mixed label-field/button rows inherit **bottom-aligned actual controls** from the single CSS primitive; do not add per-ID offsets, margins or tab-specific fixes. For layout edits, run `tests/manual/control_alignment_browser.cjs` across real Chromium viewport widths with the [isolated browser fixture](docs/aapanel-integration.md#isolated-browser-regression); it exercises the same real task routes as the layout runner. Keep the static UI contract test green.
- For isolated aaPanel Browser QA, read the [verified protected login runbook](docs/aapanel-integration.md#native-authenticated-browser-qa-runbook-aapanel-807) **before** attempting `browser_session_credential_login`: aaPanel 8.0.7 uses post-login `#app`, not legacy `.main-content`. Treat old `credential_login_not_confirmed` entries as historical until independently reproduced on the current guest. Never export protected credentials or session tokens.
- **One persistent QA VM (Owner decision):** Before any real native acceptance, read the active contract at [Issue #21](https://github.com/AChWorks/ach-aapanel-customizer/issues/21). Reuse the already-identified `ach-aapanel-qa/aac-native-qa-20261118` on AI Test Server; do not create, clone, replace, stop or delete that VM, or create fresh disposable VM snapshots while development continues. The existing protected aaPanel `service_access` credential is the login path; never reset it for ordinary QA. Tests may use **task-owned sites/fixtures within the retained VM**, with exact pre-state and peer-site preservation. Historical other-guest tests do not establish installed-current-HEAD acceptance here. Any intentional replacement or stop requires a new Owner decision.
- **Source-of-truth navigation:** This README maps authority. [#2](https://github.com/AChWorks/ach-aapanel-customizer/issues/2) owns accepted feature backlog, [#10](https://github.com/AChWorks/ach-aapanel-customizer/issues/10) owns unknown-host HTTPS/443 policy, and [#21](https://github.com/AChWorks/ach-aapanel-customizer/issues/21) owns the sole QA environment and remaining native acceptance. Read top-level active issue contracts, not superseded dated comment checklists; inspect live source and runtime separately.
- Preserve repository approval gates: stable candidate, relevant automated validation, independent review where required, and separate explicit Owner authorization for Merge, public Release and Production deployment.
